## Secrets and authentication

`JWT_SECRET` signs dashboard sessions. `NODE_REGISTRATION_KEY` is only for bootstrapping new nodes. `VPN_TOKEN` authenticates VPN hooks and registration through `X-VPN-Token`. `AGENT_SECRET_TOKEN` authenticates the Agent with `Authorization: Bearer <token>`. Treat all of them as high-value passwords.

Use a cryptographic generator such as `openssl rand -hex 32`, store values in a secret manager or access-restricted `.env` file, and rotate them when compromise is suspected. JWT rotation can invalidate sessions; rotating a VPN token or registration key requires updating the nodes or processes that use it. Plan rotation so nodes do not lose connectivity simultaneously.

Authentication cookies are HTTP-only and tokens have an expiry. Rate limiting, CORS, and audit logging strengthen security, but they do not replace HTTPS, firewalls, OS updates, and restricted dashboard access.

## Daily operations

```bash
cd /opt/vpn-manager
docker compose ps
docker compose logs -f manager
docker compose pull
docker compose up -d

# Native Agent
systemctl status vpn-agent
journalctl -fu vpn-agent
systemctl status vpn-coredns

# Docker Agent
docker logs -f vpn-agent
systemctl status openvpn-server@server
systemctl status wg-quick@wg0
```

The Manager health endpoint is `/api/v1/health`. The production container has an internal health check. Nodes normally send a heartbeat every 30 seconds; the Manager checks nodes every 60 seconds and marks them offline after 120 seconds without a heartbeat.

## Backup and recovery

Backups must include application data, `/opt/vpn-manager/.env`, and any reverse-proxy or PKI material needed to restore service. Store backups outside the Manager host and protect them as secrets.

### Create a backup

Run this on the Manager host. Stopping the Manager prevents writes while the Docker volume is archived.

```bash
sudo install -d -m 700 /opt/vpn-manager/backups
cd /opt/vpn-manager
VOLUME="$(docker volume ls -q --filter label=com.docker.compose.volume=manager_data)"
test -n "$VOLUME"
docker compose stop manager
sudo tar -C "$(docker volume inspect "$VOLUME" --format '{{ .Mountpoint }}')" \
  -czf "backups/manager-data-$(date +%F-%H%M%S).tar.gz" .
sudo cp .env "backups/manager-env-$(date +%F-%H%M%S).env"
docker compose start manager
```

Verify the archive before relying on it:

```bash
tar -tzf /opt/vpn-manager/backups/manager-data-YYYY-MM-DD-HHMMSS.tar.gz
curl -f http://localhost:3000/api/v1/health
```

The archive contains the SQLite database and is not encrypted. Encrypt it at rest or store it only in an access-controlled backup system.

### Restore a backup

Restoring replaces all current Manager data. Stop first, retain a copy of the current volume, and restore only a backup made by a compatible application version.

```bash
cd /opt/vpn-manager
VOLUME="$(docker volume ls -q --filter label=com.docker.compose.volume=manager_data)"
test -n "$VOLUME"
docker compose down
docker volume rm "$VOLUME"
docker compose create
VOLUME="$(docker volume ls -q --filter label=com.docker.compose.volume=manager_data)"
sudo tar -C "$(docker volume inspect "$VOLUME" --format '{{ .Mountpoint }}')" \
  -xzf backups/manager-data-YYYY-MM-DD-HHMMSS.tar.gz
sudo install -m 600 backups/manager-env-YYYY-MM-DD-HHMMSS.env .env
docker compose up -d
curl -f http://localhost:3000/api/v1/health
```

Test restores on an isolated host before an incident. A restored database reverts users, nodes, credentials, policies, and audit history to the backup point; Agents whose credentials changed after that point may need to be registered again.

Do not run `docker compose down -v` in production unless data is intentionally being deleted: it removes database volumes.

## Updates and uninstalling

Before updating, create a backup, record the release or image version, and check node status. Update the Manager with `docker compose pull && docker compose up -d`. Update nodes with `scripts/update-node.sh`; it detects native systemd and Docker Compose deployments while retaining `/opt/vpn-agent/.env` credentials. Use `scripts/uninstall-manager.sh` or `scripts/uninstall-agent.sh` only after verifying their impact and creating a backup.

## Failed tasks

The **Tasks** dashboard lists pending, completed, and failed Agent work. Open a failed task to inspect its error and select **Retry task** to create a new pending task with the validated original payload. Retrying never duplicates an equivalent task that is already pending or running. Resolve the underlying node, VPN, firewall, or Manager connectivity problem before retrying.
