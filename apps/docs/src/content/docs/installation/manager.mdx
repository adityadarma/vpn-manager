title: Install the Manager

## Prerequisites

Use Linux with `root` or `sudo` access, Docker Engine, and Docker Compose v2. The installation script does not install Docker.

```bash
docker --version
docker compose version
```

The Manager and VPN Node can run on the same host, but separate nodes are safer and scale more easily. Complete the Manager installation before installing a node because the node needs the Manager URL, VPN token, and registration key.

## Production installation

Run this on the Manager host:

```bash
curl -fsSL https://raw.githubusercontent.com/adityadarma/vpn-manager/main/scripts/install-manager.sh | sudo bash
```

The script creates `/opt/vpn-manager`, downloads `docker-compose.prod.yml`, creates `.env` when it does not exist, selects a database, and starts the containers. Reinstallation preserves `.env` so existing secrets, database settings, nodes, and sessions remain unchanged.

### Release channels

The command above installs the stable `latest` channel. To test the moving beta channel instead, add `CHANNEL=beta`:

```bash
curl -fsSL https://raw.githubusercontent.com/adityadarma/vpn-manager/main/scripts/install-manager.sh | \
  sudo bash -s -- CHANNEL=beta
```

The beta installer sets `IMAGE_VERSION=beta` in `/opt/vpn-manager/.env`, so subsequent installer updates remain on beta. The release workflow publishes `ghcr.io/adityadarma/vpn-manager:beta` whenever a beta prerelease tag (such as `v1.1.8-beta`) is pushed. Beta is for testing and can change without a stable release; use the default channel for production.

Choose one of these databases when prompted:

| Option | `DATABASE_TYPE` value | Use case |
| --- | --- | --- |
| SQLite | `sqlite` | Small, simple installations; data is stored in the `manager_data` volume |
| PostgreSQL | `postgres` | Production with the bundled database container or an external service |
| MariaDB | `mysql` | Environments using MySQL/MariaDB compatibility |

On a new interactive install, the script asks for the initial `admin` password without echoing it on the terminal. Enter a password of at least eight characters, or press Enter to generate a strong random password. An auto-generated password is printed once in the final summary; a password you enter yourself is not printed again. Store the application URL, `NODE_REGISTRATION_KEY`, and `VPN_TOKEN`, then change the admin password after first login.

The Manager serves the Web UI and API from one public origin, not separate URLs. For example, when the application URL is `https://vpn.example.com`, the dashboard is at `https://vpn.example.com` and the API is at `https://vpn.example.com/api/v1/...`. The installer only asks for the Manager HTTP port; domain, DNS, reverse-proxy, and TLS configuration remain under the administrator's control. Point a reverse proxy at `http://127.0.0.1:<PORT>` and terminate TLS there. Runtime deployment uses `PORT`; production is same-origin, so `WEB_URL` is not required for API/UI communication.

## Access and TLS

The container serves HTTP on `PORT`, `3000` by default. For public access, terminate TLS at Nginx, Caddy, Traefik, Cloudflare Tunnel, or another reverse proxy, then forward traffic to `http://manager:3000` or host port `3000`. Ensure the proxy forwards `X-Forwarded-*` headers; the application trusts proxy headers for client identity.

Do not expose the administrative dashboard to the internet without HTTPS, strong authentication, and network restrictions where possible.

## Manual Compose deployment

Copy `.env.example` to `.env`, set strong secrets, then start the production Compose file.

```bash
cp .env.example .env
openssl rand -base64 32
openssl rand -hex 32
docker compose -f docker-compose.prod.yml up -d
```

For bundled databases, the Compose profile must match `DATABASE_TYPE`:

```bash
docker compose -f docker-compose.prod.yml --profile postgres up -d
docker compose -f docker-compose.prod.yml --profile mariadb up -d
```

The profile is named `mariadb`, while the application value remains `DATABASE_TYPE=mysql`. For an external database, set `DATABASE_URL` to the external server URL and do not enable a local database profile.

## Local development

Prerequisites: Node.js `>=24`, pnpm `>=9`, and Git.

```bash
git clone https://github.com/adityadarma/vpn-manager.git
cd vpn-manager
pnpm install
cp .env.example .env
pnpm db:migrate
pnpm db:seed
pnpm dev
```

The API is available at `http://localhost:3000`, the Vite dashboard at `http://localhost:5173`, and development Swagger at `http://localhost:3000/docs`. Set `ADMIN_PASSWORD` before `pnpm db:seed`, or save the random password printed by the seed process.

## Uninstall

Create a backup first if the data matters. Run this on the Manager host:

```bash
curl -fsSL https://raw.githubusercontent.com/adityadarma/vpn-manager/main/scripts/uninstall-manager.sh | sudo bash
```

Or, if you already have the repository checked out:

```bash
sudo bash scripts/uninstall-manager.sh
```

The script prompts for:

1. **Uninstall mode** — `Full remove` deletes containers, images, database volumes, and `/opt/vpn-manager`. `Keep data` deletes containers and images but keeps the database volumes (`manager_data`, and `postgres_data`/`mariadb_data` if used), so a later reinstall can restore the same data.
2. **Backup before uninstalling** — if `/opt/vpn-manager/backup.sh` exists, offers to run it before anything is removed.
3. **Remove Docker images** — deletes the local `ghcr.io/adityadarma/vpn-manager:latest` image.
4. **Remove the installation directory** — deletes `/opt/vpn-manager` (skipped automatically in `Keep data` mode).
5. **Remove cron jobs** — removes any crontab entries that reference `vpn` (for example, a scheduled backup job), after showing them for confirmation.

The script does not remove your reverse proxy configuration or TLS certificates; clean those up manually if the domain is no longer in use. To reinstall afterwards, run `install-manager.sh` again — a `Keep data` uninstall followed by a fresh install using the same database settings restores the previous state.
